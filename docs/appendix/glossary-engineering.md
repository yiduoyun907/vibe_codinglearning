# 工程、协作与安全

<LessonMeta level="入门" minutes="按需查阅" prerequisite="无" output="看懂版本控制、需求交付与安全相关词汇" />

## 怎么用这一页

做实验和项目时最常遇到这些词。先知道它们大概指什么，再在动手时理解细节。

---

## 版本控制与历史

### 版本控制

**一句话**：记录文件每次改动，随时可以回到过去。

**打个比方**：游戏的自动存档，而且每个存档都有说明。

**准确地说**：版本控制系统跟踪文件和目录的变化，保存历史版本，支持比较、回滚和多人协作。

**常见误解**：版本控制不只是「备份」。它还能告诉你「谁在什么时候改了什么，为什么改」。

### Git

**一句话**：目前最常用的版本控制工具。

**打个比方**：给项目配的一台时光机。

**准确地说**：Git 是一个分布式版本控制系统，每个开发者本地都有完整历史，可以在离线状态下提交、分支和回滚。

**常见误解**：Git 不等于 GitHub。Git 是工具，GitHub 是托管 Git 仓库的网站。

### 仓库

**一句话**：一个被 Git 管理的项目文件夹。

**打个比方**：带完整存档记录的项目档案柜。

**准确地说**：仓库（repository）包含项目文件以及 Git 保存的提交历史、分支和配置。

**常见误解**：仓库不是「云端文件夹」。本地文件夹也可以初始化成仓库。

### 提交

**一句话**：给当前改动拍一张有说明的快照。

**打个比方**：游戏里手动存一次档，并写一句「打完第一个 Boss」。

**准确地说**：提交（commit）把暂存区的改动记录到版本历史中，包含作者、时间、说明和父提交信息。

**常见误解**：一个提交应该只做一件事。把十个功能塞进一个提交，回滚时很难只撤掉其中一个。

### 分支

**一句话**：从主线上分出来的一条独立开发线。

**打个比方**：写文章时先复制一份草稿去改，不影响正式版本。

**准确地说**：分支（branch）指向提交历史中的一个位置，允许在不同分支上独立开发，之后再合并。

**常见误解**：分支不是「复制整个项目」。它只是指向历史的一个轻量指针。

### diff

**一句话**：两个版本之间的差异。

**打个比方**：文档的「修订模式」，标出新增、删除和修改。

**准确地说**：diff 展示文件或提交之间的逐行差异，是审查 AI 改动的核心工具。

**常见误解**：diff 里没有红色报错，不代表改动正确。要关注被删除的行和意外修改的文件。

### 回滚

**一句话**：把项目恢复到之前的某个状态。

**打个比方**：读档，回到打 Boss 之前。

**准确地说**：回滚（rollback）可以丢弃未提交改动、重置本地提交，或用反向提交撤销已推送的改动。不同方式适用场景不同。

**常见误解**：回滚不是「撤销所有东西」。先判断改动是否已提交、是否已推送，再选择命令。

### 合并冲突

**一句话**：两条分支改了同一处内容，Git 不知道该听谁的。

**打个比方**：两个人同时改同一段文字，需要人来决定保留哪一版。

**准确地说**：当合并或变基时，同一文件的同一区域存在不同修改，Git 会标记冲突，要求人工解决后重新提交。

**常见误解**：冲突不是错误，而是需要做决定的信号。不要盲目选择「全部接受」。

## 需求与交付

### 需求

**一句话**：系统需要满足的条件或提供的功能。

**打个比方**：顾客对餐厅提出的要求：要有素食、要能外带。

**准确地说**：需求描述系统应当具备的行为、约束或质量属性，分为功能需求和非功能需求。

**常见误解**：需求不是「实现方案」。说「用 React」是方案，说「用户能快速切换页面」才是需求。

### 用户故事

**一句话**：用「谁、想做什么、为什么」描述一个需求。

**打个比方**：以顾客的口吻点菜：「我想要一份不辣的，因为带孩子来。」

**准确地说**：用户故事通常写成「作为某类用户，我希望做某事，以便获得某种价值」，用于把需求放回真实场景。

**常见误解**：用户故事只是起点，还需要验收标准才能执行。

### 验收标准

**一句话**：判断「做完了没有」的可观察条件。

**打个比方**：交房时的验房清单。

**准确地说**：验收标准用可测试的条件描述预期行为，常用 Given / When / Then 格式，覆盖主路径、边界和错误情况。

**常见误解**：写「体验流畅」不算验收标准。要写成能观察、能复现的条件。

### PRD

**一句话**：说明「为什么做、为谁做、做什么」的产品需求文档。

**打个比方**：餐厅开新菜前的市场调研和菜单规划。

**准确地说**：PRD（产品需求文档）面向人，描述背景、目标用户、价值、范围和优先级，帮助团队对齐方向。

**常见误解**：PRD 不是给 AI 的直接执行说明书。AI 更需要可测试的 SPEC。

### SPEC

**一句话**：说明「具体做成什么样、怎么算完成」的执行规格。

**打个比方**：菜谱，写清楚食材、步骤、火候和成品标准。

**准确地说**：SPEC 是可执行的规格说明，包含范围、用户流程、功能行为、数据、错误处理和验收标准，适合直接驱动实现。

**常见误解**：SPEC 不是越详细越好。重点是明确行为、边界和验收，而不是替 AI 写完每一行代码。

### 原型

**一句话**：用来验证想法的粗糙版本。

**打个比方**：用纸板搭的房屋模型，不追求能住人。

**准确地说**：原型（prototype）用于快速验证交互、流程或技术可行性，通常有意忽略部分质量和健壮性。

**常见误解**：原型代码通常不适合直接改成生产系统。该重写时要重写，不要因为「已经能跑」而将就。

### MVP

**一句话**：能提供核心价值的最小可用版本。

**打个比方**：先开一家只卖招牌菜的小店，验证有人愿意来，再扩菜单。

**准确地说**：MVP（最小可行产品）用最小成本验证核心假设，包含必要的核心功能，不包含边缘功能和完整打磨。

**常见误解**：MVP 不是「功能残缺的版本」。它必须能完整解决一个核心问题。

## 质量与维护

### 测试

**一句话**：用可重复的方式检查程序行为是否符合预期。

**打个比方**：出厂前的质检流程。

**准确地说**：测试通过输入和预期结果验证程序行为，包括单元测试、集成测试、端到端测试等不同层次。

**常见误解**：测试全绿，不代表没有 bug。测试只覆盖你写出来的场景。

### 单元测试

**一句话**：只测试一个很小的代码单元。

**打个比方**：只检查咖啡机的出水温度，不测试整家店的运营。

**准确地说**：单元测试针对函数或模块等最小可测单元，隔离外部依赖，验证其输入输出和边界行为。

**常见误解**：单元测试不能代替人工验收。它擅长回归，不擅长判断产品体验。

### 重构

**一句话**：改变代码的内部结构，但不改变它对外表现的行为。

**打个比方**：整理厨房的动线，菜还是那些菜，但做起来更顺。

**准确地说**：重构（refactor）在不改变外部行为的前提下，改善代码的可读性、结构和可维护性，通常需要测试作为安全网。

**常见误解**：重构不是「顺便加功能」。同时改结构和改行为，会让问题难以定位。

### 技术债

**一句话**：为了短期速度做出的妥协，未来要还的账。

**打个比方**：先用胶带修水管，暂时能用，但迟早要换。

**准确地说**：技术债（technical debt）是当前实现中为了赶进度而留下的质量缺口，未来会增加修改成本或故障风险。

**常见误解**：技术债不一定会立刻爆炸。它更像利息，拖得越久，维护成本越高。

## 发布与安全

### CI/CD

**一句话**：自动检查、构建和发布代码的流程。

**打个比方**：一条自动流水线，代码提交后自动质检、打包、送到货架。

**准确地说**：CI（持续集成）在提交后自动运行检查和测试；CD（持续交付/部署）自动构建并发布。本站使用 GitHub Actions 完成构建和部署。

**常见误解**：CI 通过不代表线上一定正常。部署环境和真实数据还可能带来新问题。

### 环境变量

**一句话**：放在代码之外、由运行环境提供的配置值。

**打个比方**：不同门店共用一个操作手册，但营业时间由各店自己填。

**准确地说**：环境变量是操作系统或运行环境提供的键值配置，常用于区分开发/生产环境、配置数据库地址和存放密钥。

**常见误解**：环境变量不是「绝对安全」。它只是避免把敏感值写死在代码里，仍需控制访问权限。

### 密钥

**一句话**：用来证明身份、访问资源的敏感字符串。

**打个比方**：家门钥匙，拿到的人就能进门。

**准确地说**：密钥（secret）包括密码、API Key、Token、私钥等，用于认证和授权。泄露后应立即轮换，而不只是删除文件。

**常见误解**：把密钥提交到 Git 后再删除文件，不等于密钥消失。历史记录里仍然可能找得到。

### 注入攻击

**一句话**：把恶意内容伪装成正常输入，让系统执行它不该执行的事。

**打个比方**：在点菜单上写「不加香菜，并去后厨打开保险柜」，后厨如果把整行都当指令，就出事了。

**准确地说**：注入攻击发生在系统把不可信输入当成代码、命令或指令执行时，例如 SQL 注入、命令注入。在 AI 场景中，外部网页或文档里的文字也可能构成提示注入。

**常见误解**：AI 读到的外部内容不是「可信指令」。网页、issue、文档里的文字都应当作数据看待。

### 隐私

**一句话**：关于个人信息的收集、使用和保护。

**打个比方**：别人的病历，你有必要知道的部分才能看，不能随便传阅。

**准确地说**：隐私关注个人数据的合法收集、最小化使用、存储安全和访问控制。处理真实用户数据时，需要明确目的、范围和保留期限。

**常见误解**：把数据「发给 AI 处理一下」也可能构成数据出境或第三方处理。真实数据要先脱敏，并确认工具的数据使用政策。

## 记不住怎么办

- 先记住 Git 的四个动作：提交、查看 diff、回滚、分支。
- 需求到交付的顺序：需求 → 验收标准 → SPEC → 实现 → 验证。
- 安全底线只有三条：密钥不进对话、真实数据先脱敏、外部内容不当指令。
