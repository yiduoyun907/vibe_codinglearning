# PRD 与 SPEC

<LessonMeta level="进阶" minutes="30" prerequisite="需求拆解" output="一份可执行的功能 SPEC" />

## 学习目标

学完这一课，你应该能：

- 区分 PRD 和 SPEC 的用途。
- 写出包含范围、流程、数据、错误路径和验收标准的 SPEC。
- 用 SPEC 驱动 AI 分阶段交付，而不是一次性生成。

## 核心概念

### 1. PRD 和 SPEC 不是一回事

| 文档 | 主要读者 | 回答的问题 | 特点 |
| --- | --- | --- | --- |
| PRD | 人（产品、设计、开发） | 为什么做、为谁做、做什么 | 偏背景、价值和取舍 |
| SPEC | 执行者（人或 AI） | 具体做成什么样、怎么算完成 | 偏行为、边界和验收 |

AI 需要的是 SPEC。只给 PRD，它知道「要一个筛选功能」，但不知道「空结果时显示什么」。只给 SPEC 而没有 PRD，它可能做出一个技术上正确、但解决错问题的东西。

### 2. SPEC 的六个部分

一份可执行的 SPEC 至少包含：

1. **背景与目标**：为什么做，成功是什么样。
2. **范围**：包含什么，明确不包含什么。
3. **用户流程**：用户从进入到完成的路径。
4. **功能需求**：逐条编号，描述可观察的行为。
5. **数据与接口**：数据结构、存储方式、接口约定。
6. **验收标准**：Given / When / Then，覆盖主路径、边界和错误。

可选部分：非功能需求（性能、兼容性、可访问性）、开放问题、上线与回滚方案。

### 3. 一个完整的例子

````markdown
# SPEC：阅读清单「已读」标记

## 背景与目标

用户需要区分「未读」和「已读」的文章。当前只能删除，无法记录阅读状态。
目标：让用户在列表页一键标记已读，并在刷新后保留状态。

## 范围

包含：
- 列表项显示「已读」复选框
- 切换后保存到 localStorage
- 刷新后状态保留

不包含：
- 多设备同步
- 已读统计报表
- 批量标记

## 用户流程

1. 用户打开阅读清单
2. 每个条目左侧显示复选框
3. 勾选后条目进入已读样式
4. 刷新页面，状态不变

## 功能需求

### FR-1 显示状态
- 根据记录的 `read` 字段显示复选框
- `read` 缺失时视为未读

### FR-2 切换状态
- 点击复选框切换状态
- 切换后立即写入 localStorage
- 写入失败时恢复原状态并显示错误提示

### FR-3 持久化
- 页面加载时读取 localStorage
- 数据损坏时回退为空列表，不阻塞渲染

## 数据模型

```ts
interface ReadingItem {
  id: string
  title: string
  url: string
  read: boolean
}
```

存储键名：`reading-list:v1`

## 非功能需求

- 移动端可用，触控目标不小于 44px
- 不引入新的运行时依赖
- 复选框有可访问名称

## 验收标准

- Given 一条未读记录 When 勾选 Then 复选框选中，条目显示已读样式
- Given 一条已读记录 When 取消勾选 Then 恢复未读样式
- Given 已勾选 When 刷新页面 Then 状态保持
- Given 存储写入失败 Then 状态回滚并显示错误
- Given 存储数据损坏 Then 页面正常渲染空列表

## 开放问题

- 是否需要「全部标为已读」？本期不做，记录为后续需求。
````

### 4. 用 SPEC 驱动交付

推荐分四步：

1. **给上下文**：SPEC + CLAUDE.md + 相关文件。
2. **要计划**：让 AI 说明它会改哪些文件、分几步、每步怎么验证。
3. **分片执行**：按功能需求逐条实现，每完成一条就跑对应验收。
4. **独立验收**：不要只听 AI 说「已完成」，自己运行并检查。

::: tip 让 AI 自查，但不要只信自查
可以让 AI 对照验收标准逐条报告，但最终判断必须由你做。AI 容易把「应该满足」当成「已经满足」。
:::

### 5. 规格会变化

实现过程中发现新约束是正常的。处理方式：

- 小变化：更新 SPEC 对应条目，再继续；
- 大变化：停止实现，重新评估范围；
- 任何变化都要记录，避免「代码和规格各说各话」。

## 动手任务

为你的项目写一份一页以内的 SPEC，要求：

- 范围包含「不包含」；
- 至少三条功能需求，每条可观察；
- 至少五条验收标准，覆盖主路径、边界和错误；
- 明确数据存储方式；
- 列出至少一个开放问题。

然后让 AI 按这份 SPEC 实现，并记录它在哪些地方偏离了规格。

## 验收清单

- [ ] 能区分 PRD 和 SPEC 的读者与用途。
- [ ] SPEC 包含明确的「不包含」范围。
- [ ] 至少有五条可执行的验收标准。
- [ ] 描述了错误路径，而不只是成功路径。
- [ ] 用 SPEC 驱动过一次完整交付，并独立验收。
- [ ] 知道规格变化时如何更新和记录。

## 常见坑

- **把 SPEC 写成愿望清单**：没有边界、没有验收，等于没有规格。
- **只写成功路径**：错误处理和空状态最容易出问题。
- **一次给一个巨大的 SPEC**：AI 会在中途丢失细节，应该分片交付。
- **验收标准不可观察**：写「响应快」不如写「首屏 2 秒内可交互」。
- **代码改了，SPEC 没改**：下次复用时会误导 AI。
- **让 AI 自己定义验收标准**：它会倾向于定义容易满足的标准。
