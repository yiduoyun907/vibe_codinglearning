# 需求拆解

<LessonMeta level="进阶" minutes="30" prerequisite="心智模型：从意图到交付" output="一份可执行的任务拆解表" />

## 学习目标

学完这一课，你应该能：

- 区分目标、需求、任务和实现四个层次。
- 用验收标准描述「完成」是什么样。
- 把一个大需求拆成可在一次会话内完成的垂直切片。

## 核心概念

### 1. 四个层次

模糊需求之所以难执行，是因为它把四个层次混在了一起：

| 层次 | 要回答的问题 | 例子 |
| --- | --- | --- |
| 目标 | 为什么做 | 让用户更快找到收藏的内容 |
| 需求 | 做什么 | 支持按标签筛选收藏 |
| 任务 | 分几步做 | 先做标签数据结构，再做筛选 UI |
| 实现 | 具体怎么写 | 用数组过滤还是查询参数 |

AI 擅长实现，能协助任务，但目标和需求必须由你定义。

### 2. 用户故事与验收标准

一个可执行的需求，至少包含：

```text
作为 <角色>，我希望 <行为>，以便 <价值>。
```

但用户故事本身不够。还需要验收标准，把「完成」写成可观察的条件：

```text
Given 收藏列表中有三个标签
When 用户选择「前端」标签
Then 只显示带有「前端」标签的条目
And 刷新页面后筛选状态保留
```

验收标准应该覆盖：

- 主路径；
- 边界情况（空列表、超长文本、重复操作）；
- 错误路径（存储失败、网络失败、权限不足）。

### 3. 非目标

明确写出「这次不做什么」，和写出「要做什么」同样重要。

非目标能防止：

- AI 自作主张扩展功能；
- 范围在实现过程中不断膨胀；
- 验收时对「为什么没做 X」产生分歧。

例如：

```text
非目标：
- 不做标签的增删改管理
- 不做多标签组合筛选
- 不做跨设备同步
```

### 4. 拆解粒度

好的任务单元满足：

- 能独立验证；
- 一次会话内能完成；
- 失败时能单独回滚；
- 不依赖另一个未完成的任务。

推荐按**垂直切片**拆：每个切片都从数据到界面打通一小条，而不是先写完所有数据层，再写所有界面。

| 不推荐 | 推荐 |
| --- | --- |
| 先做完整数据模型 | 先做「显示一条固定数据」 |
| 再做完整 API | 再做「读取真实数据」 |
| 最后做界面 | 再做「添加一条数据」 |

### 5. 遇到未知时先做实验

如果某个技术点不确定，不要把它写进正式任务。先做一个最小实验（spike）：

- 只验证一个问题；
- 设定时间盒，例如 30 分钟；
- 记录结论，决定继续或换方案；
- 实验代码可以不保留。

## 动手任务

选一个你想做的功能，按下面的模板拆解：

```markdown
## 目标
<为什么做，成功是什么样>

## 用户故事
作为 ____，我希望 ____，以便 ____。

## 验收标准
- Given ____ When ____ Then ____
- Given ____ When ____ Then ____

## 非目标
- 不做 ____
- 不做 ____

## 任务拆分
| 序号 | 任务 | 产出 | 验收方式 |
| --- | --- | --- | --- |
| 1 | | | |
| 2 | | | |
| 3 | | | |

## 约束
- 技术栈：
- 兼容性：
- 性能：
- 安全与隐私：

## 开放问题
- ____
```

要求：任务不超过五个，每个任务都能在一次会话内完成。

## 验收清单

- [ ] 能区分目标、需求、任务和实现。
- [ ] 每个需求都有至少一条可观察的验收标准。
- [ ] 写下了明确的非目标。
- [ ] 任务粒度满足「一次会话内可验证」。
- [ ] 不确定的技术点被拆成独立实验，而不是混进主任务。

## 常见坑

- **只写功能，不写非功能**：性能、兼容性、安全要求不写，AI 不会主动考虑。
- **把实现方案当需求**：需求应描述行为，不是指定代码结构。
- **没有非目标**：范围会在实现过程中悄悄膨胀。
- **任务太大**：一次让 AI 做五个模块，结果无法逐项验证。
- **忽略错误路径**：只描述成功情况，失败时行为不可预期。
- **验收标准不可观察**：写「体验流畅」不如写「首屏在 2 秒内可交互」。
