# 需求拆解

<LessonMeta level="进阶" minutes="30" prerequisite="心智模型：从意图到交付" output="一份可执行的任务拆解表" />

## 学习目标

学完这一课，你应该能：

- 分清「目标、需求、任务、实现」四个层次。
- 用验收标准说清「做完是什么样」。
- 把一个大需求拆成几个能单独验证的小任务。

## 一句话理解

**不要把「我想做个待办清单」直接丢给 AI，而是拆成「先做一个能显示三条假数据的列表」这样能立刻验证的小步。**

## 核心概念

### 1. 四个层次

模糊需求之所以难做，是因为它把四件事混在了一起：

| 层次 | 要回答的问题 | 例子 |
| --- | --- | --- |
| 目标 | 为什么做 | 让我不再忘记每天要做的事 |
| 需求 | 做什么 | 能添加、勾选、删除待办 |
| 任务 | 分几步做 | 先显示假数据，再做添加，再做勾选 |
| 实现 | 具体怎么写 | 用数组存数据，还是用浏览器存储 |

AI 擅长「实现」，能协助「任务」，但「目标」和「需求」必须由你定。

### 2. 用户故事：把需求放回场景

一个简单的写法：

```text
作为 <谁>，我希望 <做什么>，以便 <得到什么好处>。
```

例如：

```text
作为一个经常忘事的人，我希望在打开页面时看到今天的待办，
以便不用再翻聊天记录找任务。
```

但用户故事还不够，它没有说「做到什么程度算完成」。

### 3. 验收标准：把「完成」写成能观察的条件

推荐用 Given / When / Then 格式：

```text
Given 列表为空
When 我输入「买牛奶」并点击添加
Then 列表出现「买牛奶」，输入框清空
```

验收标准要覆盖三类情况：

- **主路径**：正常操作能不能成功。
- **边界**：空输入、超长文字、重复点击。
- **错误**：保存失败、网络失败、权限不足时，页面怎么表现。

::: tip 判断标准
如果一个条件无法通过「看、点、运行」来确认，它就不是合格的验收标准。
:::

### 4. 非目标：明确「这次不做什么」

写清楚不做什么，和写清楚做什么一样重要。

非目标可以防止：

- AI 自作主张扩展功能；
- 做着做着范围越来越大；
- 验收时争论「为什么没做某个功能」。

例如：

```text
非目标：
- 不做账号系统
- 不做多设备同步
- 不做批量导入
```

### 5. 拆解粒度：一次只做一个能验证的切片

好的任务单元满足：

- 能单独验证；
- 一次会话内能完成；
- 失败时能单独撤销；
- 不依赖另一个还没完成的任务。

推荐按「垂直切片」拆：每个切片都从数据到界面打通一小条，而不是先写完所有数据层，再写所有界面。

| 不推荐 | 推荐 |
| --- | --- |
| 先做完整的数据模型 | 先显示三条假数据 |
| 再做完整的接口 | 再读取真实数据 |
| 最后做界面 | 再做添加一条数据 |

### 6. 遇到不确定的技术点，先做小实验

如果某个技术点你不确定，不要把它塞进正式任务。先做一个「小实验」：

- 只验证一个问题；
- 限时，例如 30 分钟；
- 记录结论；
- 实验代码可以丢掉。

## 动手任务

选一个你想做的功能，按下面的模板拆解。要求任务不超过五个，每个都能在一次会话内完成。

```markdown
## 目标
<为什么做，成功是什么样>

## 用户故事
作为 ____，我希望 ____，以便 ____。

## 验收标准
- Given ____ When ____ Then ____
- Given ____ When ____ Then ____

## 非目标
- 不做 ____
- 不做 ____

## 任务拆分
| 序号 | 任务 | 产出 | 怎么验证 |
| --- | --- | --- | --- |
| 1 | | | |
| 2 | | | |
| 3 | | | |

## 限制
- 技术限制：
- 兼容性：
- 性能：
- 安全与隐私：

## 还不确定的问题
- ____
```

## 验收清单

- [ ] 能分清目标、需求、任务和实现。
- [ ] 每个需求至少有一条可观察的验收标准。
- [ ] 写下了明确的非目标。
- [ ] 每个任务都能在一次会话内验证。
- [ ] 不确定的技术点被拆成独立小实验，而不是混进主任务。

## 卡住了怎么办

- **目标写不出来**：先写「谁在什么情况下会遇到什么问题」。
- **验收标准太虚**：改成「我点哪里、看到什么、发生什么」。
- **任务拆不小**：先做「只显示假数据」的版本，能跑再继续。
- **不知道非目标写什么**：问自己「这次最容易被带偏去做什么」。

## 常见误解

- **只写功能，不写限制**：性能、兼容性、安全要求不写，AI 不会主动考虑。
- **把实现方案当需求**：需求描述行为，不是指定代码结构。
- **没有非目标**：范围会在实现过程中悄悄膨胀。
- **任务太大**：一次让 AI 做五个模块，结果无法逐项验证。
- **忽略错误路径**：只描述成功情况，失败时行为不可预期。
