# Vibe Coding 是什么，不是什么

<LessonMeta level="入门" minutes="15" prerequisite="无" output="一段你自己的审查底线" />

## 学习目标

学完这一课，你应该能：

- 说出 Vibe Coding 的原始定义，而不是把它等同于「AI 帮我写代码」。
- 区分「不审查的 Vibe Coding」和「有审查的 AI 辅助开发」。
- 写出自己的审查底线。

## 一句话理解

**Vibe Coding 是「接受 AI 写的代码，但不再逐行审查」的一种特定做法，不是所有 AI 编程的总称。**

## 先看一个场景

你想做一个只给自己用的记账小工具。你把需求告诉 AI，它写完，你打开页面试一下，能用就继续。你没有读代码，也没有写测试。

这很接近 Vibe Coding 的原始用法。

但如果这个工具要给同事用、要处理真实账目，同样的做法就危险了。区别不在于「你有没有用 AI」，而在于**你有没有审查、测试，并能为结果负责**。

## 核心概念

### 1. 原始定义

2025 年 2 月，Andrej Karpathy 用一个说法描述一种新的编程方式：

> 「完全交给感觉，拥抱指数级变化，忘记代码的存在。」

他描述了几个具体动作：

- 一直点「全部接受」，不再读 diff；
- 报错就直接复制粘贴给 AI，不加说明；
- 修不好就绕过，或者让 AI 随便改到它消失；
- 承认代码已经超出了自己的理解范围。

他同时说，这适合「一次性周末项目」。

::: details 证据卡｜Karpathy 的原始表述
- **来源类型**：专家观点，一手来源
- **支持什么**：Vibe Coding 最初指的是一种不审查、跟着感觉走的编程方式
- **适用边界**：个人周末项目、低风险实验；不是生产环境方法论
- **对本站的含义**：不能把「用了 AI」直接等同于「Vibe Coding」
:::

### 2. 它是一条光谱

把 AI 协作方式分成三档，比二元标签更有用：

| 类型 | 你怎么做 | 适合什么 | 审查强度 |
| --- | --- | --- | --- |
| Vibe Coding | 接受 AI 输出，基本不读代码 | 一次性脚本、周末玩具 | 低 |
| AI 辅助开发 | AI 写初稿，你审查关键逻辑 | 日常开发、学习项目 | 中 |
| 智能体工程 | AI 执行，你负责规格、验证和交付 | 生产代码、真实用户 | 高 |

「智能体工程」（Agentic Engineering）是 Simon Willison 等人用来描述有纪律的 AI 协作的说法：你仍然对架构、质量和结果负责，只是把执行更多地交给 AI。

::: details 证据卡｜Simon Willison 的审查定义
- **来源类型**：专家观点
- **支持什么**：如果 AI 写了代码，但你审查、测试过，并且能向别人解释它，那就不是 Vibe Coding，而是软件开发
- **适用边界**：这是行业专家的操作性定义，不是实证研究
- **对本站的含义**：分界线在「生成之后做了什么」，不在「有没有用 AI」
:::

### 3. 为什么这个词容易被误用

Vibe Coding 走红后，媒体和厂商经常把它当成「所有 AI 编程」的代名词。这会造成两个误解：

- 一边认为「用 AI 就是不负责任」；
- 另一边认为「AI 写得快，所以不用学工程」。

两种都偏了。更准确的说法是：**Vibe Coding 是光谱的一端，不是全部。**

::: details 证据卡｜DORA 2025：AI 放大原有的工程实践
- **来源类型**：行业调查（近 5,000 名技术从业者）
- **支持什么**：AI 采用与吞吐量正相关，但也与交付稳定性负相关；强版本控制、小批量交付、清晰流程能放大收益
- **适用边界**：问卷为主，相关而非因果；面向团队和组织
- **对本站的含义**：AI 不是替代工程习惯，而是放大工程习惯
:::

### 4. 可以放手，但不能放弃责任

「不读代码」可以是一种工作方式，但需要同时满足四个条件：

- 失败的代价足够低；
- 你能通过运行结果判断它对不对；
- 出问题时可以快速回滚；
- 不涉及敏感数据和高风险决策。

只要有一条不满足，就必须把审查补回来。

::: warning 先记住这一句
**AI 可以替你写代码，但不能替你承担后果。**
:::

## 动手任务

把下面三个场景分别归入「Vibe Coding / AI 辅助开发 / 智能体工程」，并写一句理由：

1. 周末做一个只给自己用的记账页面。
2. 给公司的支付流程加一个退款按钮。
3. 跟着教程做一个练习项目，做完要能向别人解释代码。

然后写一句你的审查底线，例如：

> 涉及真实用户数据或支付的代码，我必须逐行审查并写测试。

## 卡住了怎么办

- **觉得概念太抽象**：回到记账小工具的场景，问自己「这段代码我敢不敢直接上线」。
- **不知道自己的项目属于哪一档**：先看最坏后果。后果小、能撤销，偏 Vibe Coding；后果大、不能撤销，偏智能体工程。
- **分不清「用了 AI」和「Vibe Coding」**：问自己有没有读代码、跑测试、能解释。三者都没有，才更接近 Vibe Coding。

## 常见误解

- **「用了 AI 就是 Vibe Coding」**：不是。关键看生成之后有没有审查和验证。
- **「Vibe Coding 一定不安全」**：低风险、可回滚的个人项目可以接受；高风险场景不行。
- **「审查了代码就不算 AI 编程」**：审查过的 AI 协作仍然是 AI 编程，只是更接近工程实践。
- **「Karpathy 说的就是最佳实践」**：他描述的是一个实验性的用法，并明确说适合一次性项目。
