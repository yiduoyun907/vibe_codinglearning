# 什么是 Vibe Coding

<LessonMeta level="入门" minutes="15" prerequisite="无" output="一段你自己的使用边界说明" />

## 学习目标

学完这一课，你应该能：

- 用一句大白话解释 Vibe Coding。
- 知道它适合做什么，不适合做什么。
- 为自己想做的一个小项目，说出哪些部分可以交给 AI，哪些必须自己把关。

## 一句话理解

**你把想做的事用大白话说给 AI，它写代码，你运行看结果，不对就继续改。**

这就是 Vibe Coding 最常见的用法。

## 先看一个场景

你想做一个记账小工具，但你不会写代码。

你可以这样开始：

> 做一个网页，可以输入一笔支出，显示金额和备注，刷新后数据还在。先给我一个能运行的最小版本。

AI 会写出文件。你打开网页，输入一笔钱，发现刷新后数据没了，于是继续告诉它：

> 刷新后数据丢失了，请把数据保存到浏览器的 localStorage 里。

它再改，你再试。这个过程，就是 Vibe Coding。

## 核心概念

### 1. 这个词是怎么来的

2025 年初，Andrej Karpathy 用一个说法描述一种新的编程方式：完全沉浸在「感觉」里，接受 AI 生成的代码，甚至不再逐行阅读。

这个词就是 **Vibe Coding**。

它一开始带有明显的实验色彩，适合周末原型、个人小工具、一次性脚本。**它不是「生产环境最佳实践」的同义词。**

::: details 准确地说
Vibe Coding 描述的是一种以自然语言驱动、快速迭代、低审查强度的编程方式。它强调的是「跟着感觉快速做出东西」，而不是一套严格的工程规范。
:::

### 2. 不要只看「怎么输入」，要看「怎么负责」

讨论 Vibe Coding 时，至少有三件事要分开看：

| 维度 | 要回答的问题 |
| --- | --- |
| 怎么和 AI 交流 | 你是用自然语言描述意图，还是逐行手写？ |
| 工作节奏 | 你是快速试错，还是先设计后实现？ |
| 风险控制 | 你是否检查生成的代码和最终行为？ |

很多人只关注第一点，忽略了第三点。

**真正的分界线是「你是否对结果负责」，不是「你是否手写代码」。**

### 3. 它是一条光谱，不是一个开关

可以把使用方式分成三档：

| 类型 | 适合什么 | 审查强度 |
| --- | --- | --- |
| 探索型 | 一次性脚本、周末原型、学习陌生工具 | 低，但要用假数据和临时目录 |
| 辅助型 | 日常开发，AI 写初稿，你改关键部分 | 中，重点看逻辑和边界 |
| 受控交付型 | 生产代码、真实用户、敏感数据 | 高，必须有规格、测试、审查和回滚方案 |

越往右，对规格、测试和审查的要求越高，而不是对「提示词技巧」的要求越高。

### 4. 可以放手，但不能放弃责任

「不读代码」是一种可以接受的工作方式，但需要同时满足四个条件：

- 失败的代价足够低；
- 你能通过运行结果判断它对不对；
- 出问题时可以快速回滚；
- 不涉及敏感数据和高风险决策。

只要有一条不满足，就必须把审查补回来。

::: warning 先记住这一句
**AI 可以替你写代码，但不能替你承担后果。**
:::

## 动手任务

拿一张纸或打开一个笔记，用三句话回答：

1. 我最近想做的一个小东西是什么？
2. 如果 AI 做错了，最坏会怎样？能不能撤销？
3. 哪些部分我可以完全交给 AI，哪些部分我要自己检查？

不需要写长，三句话就够。把答案放进你的[学习日志](/log/)。

## 卡住了怎么办

- **觉得概念太抽象**：回到上面的记账小工具场景，把它套进去想一遍。
- **不知道自己的项目属于哪一档**：先按「最坏后果」判断。后果小、能撤销，就偏探索型；后果大、不能撤销，就偏受控型。
- **担心自己不会判断**：先学下一课[心智模型](/guide/core/mental-model)，它会给你一个四步框架。

## 常见误解

- **「Vibe Coding 就是不用负责」**：不是。它只是把执行交给 AI，责任仍在你这。
- **「能跑就是对的」**：能跑只说明主路径没报错，边界和错误处理仍可能有问题。
- **「原型能跑，就能直接上线」**：原型和产品的质量标准不同，中间需要补测试、错误处理和审查。
- **「只有不会编程的人才用」**：会编程的人也在用，只是他们更清楚哪里需要检查。
