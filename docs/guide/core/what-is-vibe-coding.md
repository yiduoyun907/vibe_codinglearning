# 什么是 Vibe Coding

<LessonMeta level="入门" minutes="15" prerequisite="无" output="一份你自己的使用边界说明" />

## 学习目标

学完这一课，你应该能：

- 用一句话解释 Vibe Coding，而不是把它等同于「AI 帮我写代码」。
- 区分「探索型使用」和「受控交付」两种模式。
- 为自己最近想做的一个项目，写下哪些部分可以放手、哪些必须审查。

## 核心概念

### 1. 这个词的来源

2025 年初，Andrej Karpathy 用一个说法描述一种新的编程方式：完全沉浸在「感觉」里，接受 AI 生成的代码，甚至不再逐行阅读。这个词就是 Vibe Coding。

它的原始语境带有明显的实验色彩：适合周末原型、个人小工具、一次性脚本。**它从来不是「生产环境最佳实践」的同义词。**

### 2. 三个维度，而不是一个标签

讨论 Vibe Coding 时，至少要区分三件事：

| 维度 | 要回答的问题 |
| --- | --- |
| 交互方式 | 你是用自然语言描述意图，还是逐行手写？ |
| 工作节奏 | 你是快速试错，还是先设计后实现？ |
| 风险控制 | 你是否审查生成的代码和最终行为？ |

很多人把第一点当成全部，忽略了第三点。真正的分水岭是**风险控制**，不是输入方式。

### 3. 一条光谱

把 Vibe Coding 看成一条光谱，比二元分类更有用：

- **探索型**：一次性脚本、原型、学习陌生 API。可以少审查，但要隔离环境、不碰真实数据。
- **辅助型**：日常开发，AI 生成初稿，你审查关键逻辑。这是大多数人的主战场。
- **受控交付型**：生产代码，必须经过规格、测试、审查和回滚预案。

越往右，对规格、测试和审查的要求越高，而不是对「提示词技巧」的要求越高。

### 4. 可以放手，但不能放弃责任

「不读代码」是一种可接受的工作方式，前提是：

- 失败的代价足够低；
- 你能通过行为验证结果；
- 出问题时可以快速回滚；
- 不涉及敏感数据和高风险决策。

只要有一条不满足，就必须把审查补回来。

## 动手任务

拿出你最近想做的一个小项目，写一段不超过 300 字的判断：

1. 它属于探索型、辅助型还是受控交付型？
2. 哪些部分可以完全交给 AI？
3. 哪些部分你必须逐行审查或亲自设计？
4. 如果 AI 做错了，最坏后果是什么？能否回滚？

把这段文字放进你的[学习日志](/log/)。

## 验收清单

- [ ] 能区分「自然语言交互」和「低风险放手」是两件事。
- [ ] 能说出至少三个不适合完全交给 AI 的场景。
- [ ] 为自己的项目写下了明确的放手边界。
- [ ] 知道探索型原型和生产代码需要不同的审查标准。

## 常见坑

::: warning 把「能跑」当成「正确」
AI 生成的代码经常能跑通主路径，但在边界条件、错误处理、并发和权限上出问题。能演示不等于正确。
:::

- **把 demo 当产品**：原型阶段的技术债，进入生产后会以指数级放大。
- **用「感觉对了」替代验收**：没有验收标准，就没有判断依据。
- **忽视依赖和许可**：AI 可能引入不必要的包，或带入许可不兼容的代码。
- **在真实数据上做实验**：探索型使用应使用隔离环境和假数据。
