# 心智模型：从意图到交付

<LessonMeta level="入门" minutes="20" prerequisite="什么是 Vibe Coding" output="一个用四层框架拆解过的真实任务" />

## 学习目标

学完这一课，你应该能：

- 用「意图 → 规格 → 执行 → 验收」四层框架拆解一次 AI 协作。
- 判断一次失败发生在哪一层，而不是笼统地说「AI 不行」。
- 把任务切到「一次一个可验证改动」的粒度。

## 核心概念

### 1. 四层框架

每一次 AI 协作都可以拆成四层：

| 层级 | 你负责什么 | 失败时的典型表现 |
| --- | --- | --- |
| 意图 | 想清楚要解决什么问题、为谁解决 | 做出来的东西不是你要的 |
| 规格 | 把意图写成可执行、可验证的描述 | AI 理解正确但实现方向跑偏 |
| 执行 | 让 AI 生成或修改代码 | 代码能跑，但结构或边界有问题 |
| 验收 | 判断结果是否满足规格 | 问题被带进下一轮，越积越多 |

大多数「AI 不好用」的抱怨，根因在前两层，而不是模型能力。

### 2. AI 是执行者，不是决策者

AI 可以：

- 把明确规格翻译成代码；
- 提出多个实现方案；
- 发现你没考虑到的边界；
- 解释报错和代码行为。

AI 不应该替你决定：

- 产品要解决什么问题；
- 哪些取舍可以接受；
- 什么算「完成」；
- 哪些数据可以碰、哪些不能。

**决策权始终在你手里。** 你给 AI 的自由度，应该与任务的错误代价成反比。

### 3. 一次只改一个可验证的点

把任务切小，不是为了让 AI 好写，而是为了让你能判断对错。

一个合格的改动单元满足：

- 只解决一个问题；
- 有明确的输入和预期输出；
- 能独立运行或测试；
- 失败时可以单独回滚。

反面例子：「帮我做一个用户系统」。正面例子：「给现有登录接口加上连续失败五次后锁定十分钟的逻辑，并提供测试」。

### 4. 上下文是工作记忆

AI 没有跨会话的长期记忆。它每次只能看到：

- 系统提示和项目指令（例如 CLAUDE.md）；
- 当前对话；
- 你显式引用的文件、命令输出和错误信息。

所以，「AI 忘了」通常不是模型问题，而是你没有把关键信息放进它的工作记忆。下一阶段的[上下文管理](/guide/spec/context-management)会专门处理这件事。

### 5. 反馈回路

有效的协作是一个循环：

```
观察现象 → 形成假设 → 做最小改动 → 验证 → 更新假设
```

不要一次改五个地方再一起验证。那样即使成功了，你也不知道是哪一处起了作用。

## 动手任务

选一个你正在做或想做的任务，用下面四行把它写完整：

```text
意图：我要为____解决____问题，成功的标志是____。
规格：输入是____，输出是____，约束是____，验收方式是____。
执行：我准备让 AI 先做的最小改动是____。
验收：我会通过____来确认它是对的。
```

如果任何一行写不出来，先补那一行，不要急着让 AI 开始写代码。

## 验收清单

- [ ] 能用四层框架解释一次真实的失败经历。
- [ ] 能把一个模糊需求切到「一次一个可验证改动」。
- [ ] 能识别哪些决定必须由自己做，不能交给 AI。
- [ ] 知道「AI 忘了」通常对应哪一类上下文缺失。

## 常见坑

::: warning 把 AI 当搜索引擎
搜索引擎返回的是信息，AI 返回的是看起来合理的答案。后者更需要验证，尤其是在 API、配置和版本相关的细节上。
:::

- **一次描述十个需求**：AI 会挑容易的部分做，或者做出一个四不像。
- **不做验收就继续**：错误会进入下一轮上下文，后续修改都建立在错误基础上。
- **期待 AI 猜隐含需求**：没有写出来的约束，AI 大概率不会遵守。
- **把「代码看起来对」当成验证**：验证要基于运行结果、测试或明确的行为观察。
