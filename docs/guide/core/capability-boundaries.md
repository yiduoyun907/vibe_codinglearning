# 能力边界：AI 何时帮你、何时拖慢你

<LessonMeta level="入门" minutes="20" prerequisite="心智模型：从意图到交付" output="一张任务风险与测量表" />

## 学习目标

学完这一课，你应该能：

- 说出 AI 的生产力效果为什么因场景而异。
- 区分主观感受和实际测量。
- 为一个任务设计最小的测量方案。
- 判断哪些任务适合交给 AI，哪些必须自己把关。

## 一句话理解

**AI 不是统一的加速器。它有时快、有时慢，取决于任务、经验、代码库和你的验证成本。**

## 核心概念

### 1. AI 常见优势与弱点

| 相对擅长 | 相对不擅长 |
| --- | --- |
| 有固定套路的代码：表单、列表、增删改查 | 模糊需求：你越模糊，它越会合理发挥 |
| 输入输出明确的函数：解析、格式化、校验 | 业务规则：财务、医疗、法律逻辑错得很自信 |
| 有测试保护的重构和批量修改 | 安全关键代码：登录、鉴权、支付 |
| 测试初稿和报错解释 | 长期架构和取舍 |
| 陌生工具的入门示例 | 没有真实测量数据的性能优化 |

这些是经验总结，不是绝对规则。下一节会看到：**同样的 AI，在不同研究里可以得出相反的生产力结论。**

### 2. 两个研究，为什么结论相反

| 维度 | GitHub Copilot RCT（2023） | METR RCT（2025） |
| --- | --- | --- |
| 任务 | 用 JavaScript 实现一个 HTTP server | 开发者自己项目中的真实 bug、功能和重构 |
| 参与者 | 95 名开发者，经验水平不一 | 16 名资深开源开发者 |
| 代码库 | 短任务，从零开始 | 熟悉的大型成熟代码库 |
| 结果 | 使用 Copilot 的组平均快 55.8% | 允许使用 AI 时平均慢 19% |

这不是「谁在撒谎」，而是**条件不同**：

- 短任务、从零开始、验证简单时，AI 可能显著提速；
- 真实项目、复杂代码库、审查成本高时，AI 可能增加总耗时；
- 经验水平也会影响结果：Copilot 研究中经验较少的开发者受益更多。

::: details 证据卡｜Copilot RCT：特定任务上快 55.8%
- **研究类型**：随机对照试验（2023）
- **任务**：用 JavaScript 实现一个 HTTP server
- **结果**：使用 Copilot 的组平均完成时间 71 分钟，对照组 161 分钟，约快 55.8%
- **边界**：短任务、基础功能测试、作者与 Microsoft/GitHub 有关联
- **对本站的含义**：AI 在某些边界清晰的任务上确实能显著提速，但不能推广到所有任务
:::

::: details 证据卡｜METR：资深开发者平均慢 19%
- **研究类型**：随机对照试验（2025 年 2–6 月）
- **样本**：16 名资深开源开发者，246 个真实任务
- **结果**：允许使用 AI 时，任务平均耗时增加 19%；开发者主观感觉快了约 20%；不到 44% 的 AI 代码未经修改被接受
- **边界**：资深开发者、熟悉的大型代码库、2025 年初的工具
- **对本站的含义**：不要假设 AI 一定提速；主观感受也可能失真
:::

### 3. 主观感受 ≠ 实际效率

METR 研究里最值得记住的不是「慢 19%」，而是：

> 开发者在体验了变慢之后，仍然觉得自己快了约 20%。

这说明「感觉很快」不能作为唯一依据。你可能把时间花在了提示、等待、审查和返工上，但这些成本不容易被主观感知。

### 4. 「几乎对」也有成本

Stack Overflow 2025 年的调查里，66% 的开发者认为 AI 的答案「几乎对，但不完全对」；45% 认为调试 AI 生成的代码更耗时。

「几乎对」比「明显错」更麻烦，因为它会让你误以为不需要检查。

::: details 证据卡｜Stack Overflow 2025：信任度与「几乎对」
- **来源类型**：大规模开发者调查（约 49,000 名受访者）
- **结果**：84% 使用或计划使用 AI；对准确性的信任降到 29%；66% 认为 AI 答案「几乎对但不完全对」；45% 认为调试 AI 代码更耗时
- **边界**：自我报告，不能直接等同于客观测量
- **对本站的含义**：验证不是形式，尤其要检查「看起来对」的部分
:::

### 5. AI 会放大你的工程习惯

DORA 2025 的结论可以用一句话概括：

> **AI 不会修复一个混乱的团队，它会放大原有的混乱；也不会凭空创造好习惯，它会放大原有的好习惯。**

对应到个人：

- 有版本控制、小步提交、测试和清晰规格 → AI 更容易帮你提速；
- 没有这些 → AI 会更快地产生更多你看不过来的改动。

::: details 证据卡｜DORA 2025：吞吐量上升，稳定性可能下降
- **来源类型**：行业调查（近 5,000 名技术从业者）
- **结果**：AI 采用与吞吐量正相关，但与交付稳定性负相关；强版本控制、小批量、清晰流程能放大收益
- **边界**：问卷为主，相关而非因果
- **对本站的含义**：工具之外，工程习惯决定最终效果
:::

## 动手任务

选三个任务，先预测 AI 会帮忙还是拖慢，再写出测量方式。

| 任务 | 预测 | 测量指标 |
| --- | --- | --- |
| 改按钮文案 | | 耗时、返工次数 |
| 写一个陌生 API 的调用示例 | | 查文档时间、首次运行成功率 |
| 改支付回调 | | 审查时间、测试覆盖、回滚预案 |

要求：

- 每个任务写一个「如果 AI 帮倒忙，我怎么发现」的信号；
- 至少有一个任务，你决定「不让 AI 直接改代码」；
- 把预测和实际结果记录下来，下周回看。

## 验收清单

- [ ] 能解释 Copilot RCT 和 METR 为什么不矛盾。
- [ ] 能说出至少三个影响 AI 生产力的条件。
- [ ] 能为一个任务写出可测量的验证方式。
- [ ] 知道「主观感觉快」不能替代实际测量。
- [ ] 能判断哪些任务必须自己审查。

## 卡住了怎么办

- **不知道怎么预测**：先看任务是否边界清晰、是否能快速验证、出错能否撤销。
- **不知道怎么测量**：记录开始和结束时间、返工次数、需要人工修改的地方。
- **觉得研究离自己太远**：用你自己的一个小任务做一次对照，比记住结论更有用。
- **拿不准要不要用 AI**：先按「最坏后果」判断，再决定审查强度。

## 常见误解

- **「AI 一定更快」**：研究结论是条件性的，不是普遍加速。
- **「别人快，我也快」**：任务、经验和代码库不同，结果可能相反。
- **「主观感觉快就是快」**：METR 研究显示，主观感受可能明显偏离实际。
- **「AI 会取代判断」**：AI 可以执行，但取舍和验收仍由你负责。
- **「研究结论可以随便推广」**：要注意样本、任务和适用边界。
