# 能力边界与风险

<LessonMeta level="入门" minutes="20" prerequisite="心智模型：从意图到交付" output="一份个人任务风险判断清单" />

## 学习目标

学完这一课，你应该能：

- 快速判断一个任务适合交给 AI 的程度。
- 识别 AI 编程中最常见的六类风险。
- 用四个维度给任务打分，决定审查强度。

## 核心概念

### 1. AI 相对擅长的任务

- **样板与重复代码**：表单、CRUD、配置、数据转换。
- **有明确输入输出的函数**：解析、格式化、校验。
- **重构与迁移**：在测试覆盖足够时，批量改名、拆分模块、替换 API。
- **测试初稿**：根据现有行为生成测试用例，再由你补充边界。
- **陌生技术的入门代码**：快速得到一个可运行的最小示例。
- **解释与定位**：读报错、解释代码、提出排查方向。

这些任务的共同点是：**结果容易验证，错误代价可控。**

### 2. AI 相对不擅长的任务

- **模糊需求**：它会把你的模糊，放大成更多的模糊。
- **领域正确性**：业务规则、财务口径、医疗或法律逻辑，错得很自信。
- **安全关键代码**：鉴权、加密、支付、权限边界。
- **长期架构**：它擅长局部最优，不擅长为两年后的维护做取舍。
- **性能优化**：没有真实 profiling 数据的优化，多半是猜测。
- **需要真实世界反馈的事**：用户研究、产品取舍、组织协作。

这些任务的共同点是：**对错不只看代码，错误代价高。**

### 3. 六类常见风险

| 风险 | 表现 | 应对 |
| --- | --- | --- |
| 幻觉 API | 调用不存在的方法、参数或配置项 | 对照官方文档和类型定义 |
| 静默行为变化 | 主路径正常，边界行为被改变 | 测试 + 人工审查 diff |
| 依赖膨胀 | 为一个小功能引入大型依赖 | 检查 package 变更，优先用现有能力 |
| 安全漏洞 | 拼接 SQL、放宽权限、硬编码密钥 | 安全审查，禁止密钥进入对话 |
| 隐私泄露 | 把真实数据、日志、密钥贴进上下文 | 脱敏，使用假数据 |
| 许可问题 | 复制来源不明的代码 | 审查来源，保留许可信息 |

### 4. 四个判断维度

给任务打分时，问四个问题：

1. **可验证性**：结果能否通过测试、运行或明确检查来确认？
2. **可逆性**：出错后能否快速回滚？
3. **影响半径**：错误会影响一个函数、一个用户，还是全部数据？
4. **数据敏感度**：是否涉及密钥、个人信息、生产数据？

判断规则：

- 四项都友好 → 可以放手，重点看结果。
- 有一项不友好 → 提高审查强度。
- 两项以上不友好，或涉及安全与真实数据 → 必须逐行审查，必要时自己写。

::: danger 一条硬规则
密钥、Token、生产数据库连接串、真实用户数据，永远不要贴进 AI 对话。需要上下文时，用脱敏样例和结构说明替代。
:::

## 动手任务

列出你当前项目中的五个任务，用下面的表格打分（1 分友好，3 分危险）：

| 任务 | 可验证性 | 可逆性 | 影响半径 | 数据敏感度 | 结论 |
| --- | --- | --- | --- | --- | --- |
| 示例：改按钮文案 | 1 | 1 | 1 | 1 | 放手 |
| 示例：改支付回调 | 3 | 3 | 3 | 3 | 自己写 + 审查 |

为分数最高的两个任务，写出你的审查方案：看哪些文件、跑哪些测试、如何回滚。

- [ ] 能说出至少三类必须自己把关的任务。

## 常见坑

- **用「它能写」推断「它写得对」**：能力展示不等于正确性保证。
- **把安全逻辑当普通业务逻辑**：鉴权和支付类代码需要专门审查。
- **只看新增代码，不看删除和修改**：静默行为变化往往藏在 diff 的修改行里。
- **在疲劳时做高风险审查**：审查质量下降时，AI 引入的问题更容易漏过。
