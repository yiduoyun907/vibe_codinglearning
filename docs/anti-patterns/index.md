# 反模式库

<LessonMeta level="入门到实战" minutes="15" prerequisite="无" output="一份属于你自己的事故清单" />

这个页面记录的不是「最佳实践」，而是**真实会出事的地方**。每发现一次，就补一条。

## 快速索引

| 反模式 | 典型症状 | 根因 |
| --- | --- | --- |
| 一次给十个需求 | 交付一个四不像 | 任务粒度太大 |
| 没有验收标准 | 「感觉不对」但说不清哪不对 | 完成定义缺失 |
| 把实现当需求 | 代码结构对了，行为错了 | 混淆 what 和 how |
| 一个会话做所有事 | AI 忘记前面的约定 | 上下文污染 |
| 把整个仓库塞进去 | 回答变慢、重点丢失 | 上下文过载 |
| 不看 diff 就提交 | 引入静默副作用 | 缺少审查 |
| 能跑就算对 | 边界和错误路径崩溃 | 验证不足 |
| 让 AI 决定架构 | 局部合理，整体不可维护 | 决策外包 |
| 密钥进入对话 | 凭据泄露 | 安全边界缺失 |
| 对共享分支 `reset --hard` | 破坏他人历史 | 回滚方式错误 |

## 需求层

### 一次给十个需求

**症状**：AI 挑容易的做，或者把它们揉成一个奇怪的实现。

**正确做法**：一次一个可验证的改动。先列清单，再逐条执行。

### 没有验收标准

**症状**：做完之后你说「不是这个意思」，但说不出具体哪里不对。

**正确做法**：动手前写下 Given / When / Then。验收标准必须可观察。

### 把实现当需求

**症状**：你指定了「用 Redux」，但真正的问题是「跨页面共享筛选状态」。

**正确做法**：先描述行为和约束，把实现方案留到计划阶段讨论。

## 上下文层

### 一个会话做所有事

**症状**：讨论完 A 功能，接着让 AI 做 B 功能，它开始引用 A 的假设。

**正确做法**：切换任务时 `/clear`。需要保留的状态写成交接笔记。

### 把整个仓库塞进去

**症状**：上下文迅速耗尽，AI 忽略关键文件。

**正确做法**：用 `@文件` 精确引用，先搜索再读取。

### 不写 CLAUDE.md

**症状**：每个新会话都要重复解释命令、约定和禁忌。

**正确做法**：用 `/init` 生成后精简，控制在 100 行以内。

## 执行层

### 不看 diff 就提交

**症状**：功能正常，但删除了错误处理、改了无关文件、引入了新依赖。

**正确做法**：每次提交前 `git diff`，逐块审查。

### 一次改太多

**症状**：出问题后无法定位是哪一处改动导致的。

**正确做法**：一个提交只做一件事。大改动拆成多个切片。

### 让 AI 决定架构

**症状**：每个局部看起来合理，整体却难以维护。

**正确做法**：架构、数据模型、依赖选择由你决定；AI 提供方案和权衡。

## 验证层

### 能跑就算对

**症状**：主路径正常，空数据、超长输入、网络失败时崩溃。

**正确做法**：验收标准覆盖边界和错误路径。至少手动模拟一次失败。

### 只测主路径

**症状**：测试全绿，线上仍然出问题。

**正确做法**：补边界、空值、重复操作、权限不足等场景。

### 依赖 AI 自查

**症状**：AI 说「已完成」，你直接接受。

**正确做法**：自己运行验收。AI 的自查只能作为线索，不能作为结论。

## 协作层

### 密钥进入对话

**症状**：把 `.env`、Token、连接串贴进上下文。

**正确做法**：使用脱敏样例。密钥一旦泄露，立即轮换，而不是只删除消息。

### 对共享分支 `reset --hard`

**症状**：本地历史看起来干净了，别人的提交消失了。

**正确做法**：已推送的历史用 `git revert`。`reset --hard` 只用于本地未推送的提交。

## 记录模板

发现新反模式时，按下面格式补充：

```markdown
### <一句话命名>

**症状**：<你观察到的现象>

**根因**：<为什么会发生>

**正确做法**：<下次怎么做>

**案例**：<日期、项目、后果>
```

::: tip 反模式比最佳实践更有价值
最佳实践往往来自别人的场景，反模式来自你自己的事故。持续记录后者，你的判断力会增长得更快。
:::
